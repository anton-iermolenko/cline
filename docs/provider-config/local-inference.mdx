---
title: "vLLM and llama.cpp"
description: "Native local providers, model settings and input counting shared by VS Code and CLI."
---

Choose **vLLM** (`vllm`) or **llama.cpp** (`llamacpp`) and enter the server's
OpenAI-compatible base URL and optional API key. Model discovery runs when the
connection changes. Both direct servers and a router preserving the selected
provider's native API are supported. Provider selection is manual.

Select a model in VS Code to activate its settings. A switch saves the outgoing
model profile and restores the target's saved profile. On first selection,
reported server metadata initializes the profile; unknown settings remain unset.
Verify maximum context and normal output before use. Context, output, thinking, sampling,
capabilities and compaction controls are saved separately for each provider,
server and model. Clearing a control restores a reported default where available.
The main settings are **Maximum context size**, **Normal output (including
thinking)**, **Compaction: Target Tokens**, and **Compaction: Summarized History Budget**.
All numeric controls are editable directly. Server/calculated defaults are grey
italic; editing a value creates an override in normal text. Clearing a value
returns to its default. Clearing a budget keeps its previous number inactive in
storage for recoverability, including across model switches. Sampling, penalties,
normal-turn thinking and **Counting margin** are under **Advanced settings**.

Setting **Reasoning support** to **Unsupported** hides the thinking, thinking-budget
and reasoning-effort controls. Their saved values remain intact, but native
requests omit reasoning parameters while support is disabled. Tool-calling
capability remains discovery metadata; it has no toggle in this form.

Maximum context must be reported by discovery or entered by the user. A missing
capacity rejects model-control saves and native requests; live native counting
also enforces the server's actual capacity. Normal output defaults to the
reported server value or 8,000 tokens. Thinking is included in this allowance.

The input compaction trigger is `context - normal output - boundary - counting
margin`. The **hard compaction cap** subtracts a further minimum iteration reserve
of `ceil(context * 2 / 15)` (13⅓% of context): 5,334 tokens at 40K, 20,000 at 150K,
and 40,000 at 300K. The reserve grows continuously with capacity, including below
40K and above 300K. It limits post-compaction size, not when normal conversation
triggers compaction. A preferred target cannot exceed this cap; configurations
whose output and reserves leave no compaction capacity are rejected.

Native counting reserves one boundary token and defaults to a 128-token counting
margin. These allowances are separate from the iteration reserve. Neither the
hard cap nor raw recent-history allocation needs a user-entered limit.

Defaults use continuous linear interpolation between these reference values
(decimal tokens); from 200K upward they stay at the last allocation. There is no
message-count threshold.

| Maximum context | Tools/instructions estimate | Summary allowance | Raw recent history estimate | Preferred compaction target |
| ---: | ---: | ---: | ---: | ---: |
| 40,000 | 10,000 | 4,000 | 10,000 | 24,000 |
| 64,000 | 10,000 | 8,000 | 14,000 | 32,000 |
| 100,000 | 10,000 | 10,000 | 25,000 | 45,000 |
| 150,000 | 10,000 | 14,000 | 40,000 | 64,000 |
| 200,000 | 10,000 | 16,000 | 60,000 | 86,000 |
| 300,000 | 10,000 | 16,000 | 60,000 | 86,000 |

The context breakdown includes normal output, boundary/margin and the remaining
iterative problem-solving space, split into the guaranteed minimum reserve and
additional space. At 150K with 8K normal output, the trigger is 141,871, the hard
compaction cap is 121,871 and the default 64K target leaves 77,871 iteration tokens
(20,000 minimum plus 57,871 additional). The UI assumes 10K tokens for tools and
instructions; runtime retention substitutes calibrated overhead estimates, and native counting
verifies the complete assembled request. The
recent-history budget is `target - summary allowance - actual overhead`, then
reduced by any protected current instruction outside the retained suffix.

Only the **latest human instruction** is explicitly protected verbatim. Older
user messages can be summarized. Protected instructions consume raw-history
space, not the summary allowance. Whole messages and tool pairs remain intact,
and a large protected instruction can make the actual result exceed the preferred
target while still fitting the hard cap. The original transcript is retained.

The summary has its **own output cap**, selected by the summary allowance rather
than normal response output. Summary requests disable native thinking. Actual
summary text can be shorter; unused summary space is not automatically backfilled.
Measured compaction results must shrink the request and fit the derived hard cap.
Legacy local input, maximum-target and explicit recent-history limit values stay
in saved profiles for recoverability but do not replace the new derived budgets.

Discovery reads catalog metadata and already-loaded model properties; it does not
load every model to fill a settings page.

The shared settings manager persists the active provider/model in
`settings/providers.json`. A new CLI process using the same Cline data directory
reads that active configuration. VS Code applies changes through its queued
session rebuild path once the current run is idle. Model selection leaves
backend weight loading to the next request. This replaces the separate
`cline-model` workflow; no helper invocation or extension reload is needed.

Native providers declare their preflight counting APIs: vLLM uses `/tokenize`;
llama.cpp uses `/v1/chat/completions/input_tokens` on versions exposing that
full-chat endpoint. The same request codec handles inference and counting,
including tools, template settings, reasoning history and image processing.
A declared counter failure stops the request; it never silently uses estimates.
A server-declared `input_token_counting: false` initializes a configuration
without counting. These configurations retain Cline's conservative estimated
budget and 90% compaction trigger, with **2,048 tokens per image**. Generic
OpenAI-compatible providers without counting retain that estimated path too.

Total output includes reasoning tokens. It is reserved once against total
context; measured compaction buffers are additional proactive headroom. The
native setting for an exact thinking budget is `thinking_token_budget` on vLLM
and `reasoning_budget_tokens` on llama.cpp. Model/template effort values can
differ; leave unknown values at server default or configure supported values.

The native path has no slow-response watchdog, continuous-usage request injection
or notification delivery. Normal final input/output/cache usage remains intact.

The feature does not change installed clients, disable an existing adapter, or
remove the old helper automatically. Switch deployment and migrate existing
profiles only after validating the feature build. Historical model-specific
values stored by the adapter are not inferred as universal server defaults.
